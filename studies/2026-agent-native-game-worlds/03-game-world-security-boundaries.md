# Game, World, Security, and experience boundaries

## 1. The corrected relationship

The earlier useful decomposition remains:

```text
Ordivon World
= real external interaction, binding, evidence, continuity, and recovery

Ordivon Security
= adversarial agency, Campaigns, opponents, deception, coevolution, and evaluation

Ordivon Game
= authoritative synthetic worlds, interaction, play, content, and experience
```

Game may simulate structures that also exist in World, and Security may run experiments over either Game or World. That does not merge their authority.

## 2. Game-owned truth

Game owns the synthetic domain facts required by one world:

- entities, bodies, places, resources, and time;
- legal Actions and state transitions;
- observation and visibility;
- relationships and content when they are domain facts;
- world events, persistence, replay, reset, and residual state;
- victory, failure, or other world-local outcomes;
- player-facing interpretation and experience.

Game does not own generic Host Task continuity or real external infrastructure truth.

## 3. Host-owned continuity

Ordivon Host owns generic durable work semantics:

- Goal and Task identity;
- participant Assignment and Attempt control;
- Context provenance;
- replaceable Harness and Provider coordination;
- Proposal admission and semantic Effect coordination;
- Dispatch, Observation, Verification, Outcome, and recovery.

A Game workload supplies domain observation, candidate meaning, coordination policy, authority attributes, World execution, and result verification. It must not grow a second generic Host because a particular world needs richer characters.

## 4. Runtime-owned execution

Runtime owns physical execution facts for experiments and external processes:

- Workspace;
- Job and Runtime Attempt;
- process state;
- cancellation;
- retained Artifact bytes;
- trusted-local reconciliation and recovery.

Game may define an experiment cell or consume an Artifact. Runtime failure must not be rewritten as an in-world outcome.

## 5. World-owned external reality

Ordivon World owns or binds facts about real external objects, paths, identities, providers, bodies, tools, and effect evidence that no synthetic Game reducer can authoritatively claim.

A Game-to-World bridge may later allow a virtual Agent or artifact to affect an owned external system. The boundary must make the transition explicit; a simulated success is not evidence of a real-world effect.

## 6. Security-owned adversarial meaning

Security owns:

- Red, Blue, neutral, and compromised roles;
- strategic objectives and Campaign continuity;
- opponent hypotheses and information conflict;
- deception and counter-deception meaning;
- adversarial capability and consequence envelopes;
- hidden evaluation identity and Scorer;
- transfer, coevolution, evaluator attack, and strategic outcome taxonomy.

Game supplies facts such as path change, hidden object state, Message delivery, body persistence, capability construction, or residual presence. Security decides whether those facts constitute reconnaissance, persistence, compromise, deception, containment, or victory.

## 7. Experience-owned value

Not every Game fact should become a Host Task or Security event.

Experience includes:

- pacing;
- atmosphere;
- audiovisual presentation;
- emotional and social legibility;
- mystery and discovery;
- player expectation;
- optionality and return motivation;
- aesthetic coherence;
- the felt meaning of an encounter or history.

These may be informed by World evidence without becoming protocol objects. A celebration, friendship, quiet place, visual motif, or surprising character behavior need not be promoted into shared infrastructure.

## 8. Shared kernel, plural verticals

A useful architecture is:

```text
Game World Kernel
├── Station Zero product
├── playground or garden
├── social or investigation world
├── exploration and creation world
└── Security range
```

The kernel should remain neutral regarding why a world exists. Vertical content and experience should remain free to diverge.

## 9. Promotion rule

A mechanism moves toward shared Host, Protocol, or reusable Game infrastructure only when:

1. it appears in at least two materially different worlds or workloads;
2. the same semantic responsibility and failure mode recur;
3. ownership and recovery remain explicit;
4. one implementation-independent conformance test is possible;
5. promotion removes more duplication and drift than it adds constraints.

Until then, memory, relationship, social scheduling, construction, narrative, or organization semantics remain local to the world that proves them.

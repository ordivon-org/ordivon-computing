# 11 — Ordivon Insertion and the R5 Gate

## R4 architectural conclusion

R4 validates Ordivon's current ownership split rather than demanding a new
security substrate.

```text
Host
  participant purpose, Task, Context, Effect, ToolGrant, Binding, UNKNOWN,
  retry/admission, and accepted completion

Runtime
  Workspace, Job, process, files, streams, Artifact, local build/test, and local
  residual truth

World-native modules and providers
  browser, cloud role, storage object, proxy, cache, DNS, route, certificate,
  provider request, Receipt, callback, and external Effect observations

Security
  attacker/defender profiles, causal hypotheses, Campaign, deception,
  contradiction, containment, recovery, and residual interpretation

Game
  designed hidden truth, controlled identities/paths/vulnerabilities, repeated
  seeds, counterfactual replay, and evaluator testing
```

## Host implications

Host should preserve:

- the participant's intended Effect independently of one network request;
- external-data provenance and trust status;
- exact acting Agent, Tool, identity, and provider Binding;
- narrow Tool grants;
- explicit `UNKNOWN` after ambiguous failure;
- reconcile-before-redispatch;
- changed Binding as a new decision;
- completion based on provider/domain evidence;
- model and policy configuration in evaluations.

Host should not become an exploit detector or global security decision system.

## Runtime implications

Runtime should enable:

- disposable parser, browser, build, and network laboratories;
- generated Tool construction without ambient credentials;
- exact source, dependency, binary, and command evidence;
- process-tree and filesystem observation;
- bounded Artifact retention;
- local teardown and residual checks.

Runtime should not infer Campaign intent from process or network anomalies.

## World implications

World-native adapters may expose:

- cloud role and object access;
- browser origin/session and Tool action;
- proxy/front/backend/cache interpretation;
- DNS, route, TLS, endpoint, and path observations;
- software/update and deployment identities;
- federation and service-principal changes;
- provider idempotency, request, Receipt, callback, and object state;
- observation method, revision, time, and invalidation.

R4 still does not prove these facts belong in one database or universal schema.

## Security implications

Security may own:

- typed AttackChain hypotheses;
- Actor and Campaign identity;
- attacker resources and preconditions;
- primitive, amplification, persistence, and objective relations;
- repeated and adaptive Trial families;
- counterfactual defensive breakpoints;
- tactical, operational, strategic, information, containment, recovery, and
  evaluator-integrity outcomes;
- residual closure classification.

Before any shared `AttackChain` object enters Protocol or Core, a second
materially different consumer must require the same stable contract and show net
benefit over study-local graphs.

## Game implications

Game is the preferred early controlled range for joining:

- front/back parser differentials;
- cloud role and object permissions;
- route, DNS, TLS, and browser decisions;
- trusted updates and identity keys;
- external data, Agent Tools, memory, and delegation;
- timeouts, retries, callbacks, and duplicate Effects;
- hidden attacker goals and defender observations;
- exact reset and residual truth.

The first useful range should remain small and designed, not a general cyber
range platform.

## No immediate product mutation

R4 is a completed knowledge baseline. It does not by itself justify modifications
to World, Security, Host, Runtime, or Game production code.

A product change requires:

1. one reproduced failure in an owned workload;
2. native mechanisms shown insufficient;
3. clear repository ownership;
4. a second consumer for shared abstractions;
5. measured benefit greater than friction;
6. rollback and deletion criteria.

## Candidate first experiment

The minimum experiment should test one chain with no public consequence:

```text
external data or request
→ controlled vulnerable intermediary
→ narrow identity or Tool authority
→ one reversible simulated Effect
→ independent verifier
→ attacker adaptation
→ defender breakpoint
→ reset and residual check
```

Three promising variants:

- Agent hijacking through external content into a Task-scoped simulated Tool;
- request-differential through a local front/back pair into a simulated private
  route;
- timeout after simulated provider commit followed by reconciliation and safe
  retry.

The experiment should compare existing Host/Runtime/Game facts against any
proposed new Security or World object.

## Constraint audit

### Retain

- maximal bounded attacker;
- capability/consequence separation;
- native authority and evidence;
- stable Effect and `UNKNOWN`;
- adaptive evaluation;
- generated Tool provenance;
- independent outcome verification;
- reconstruction and residual closure.

### Do not promote yet

- universal AttackChain service;
- global vulnerability database;
- Scanner or WAF;
- central SIEM;
- identity or network controller;
- mandatory review for reversible local research;
- assumptions that one model's refusal is a security guarantee;
- assumptions that one CVE or IOC defines the Campaign.

### Deletion tests

Delete or localize a proposed R4-derived abstraction if:

- a study-local graph is enough;
- native product/Provider records express the relation;
- only one case consumes it;
- it cannot bind evidence and uncertainty;
- it duplicates ATT&CK, CWE, provider, or incident data;
- it creates a blocking control plane;
- it does not improve prevention, detection, recovery, or evaluation decisions.

## R5 route

R5 should move from literature reconstruction to a **minimal owned adversarial
range and comparative experiment contract**.

The central question is:

> Can existing Host, Runtime, Game, World adapters, and independent verifiers
> reproduce one cross-layer chain, measure adaptive Red/Blue behavior, and close
> residual state without adding a new permanent Security platform?

R5 should specify:

```text
owned topology and authoritative hidden truth
Red and Blue capability profiles
exact vulnerable and fixed revisions
one reversible Effect
attempt count and adaptation rules
independent observer and evaluator
stop/reset/rebuild protocol
residual-state proof
baseline comparisons
deletion outcomes
```

It must not begin with public targets, uncontrolled malware, live credentials, or
irreversible Effects.

## Completion criteria

R4 is complete when:

- at least five materially different official cases fit the R0–R3 grammar;
- CVE, primitive, authority amplification, Campaign, recovery, and residual are
  distinct;
- model/Host policy behavior is a configuration variable;
- defensive breakpoints are tied to graph edges;
- no universal security platform is promoted;
- R5 has a narrow experiment and deletion question.

These criteria are satisfied by this study.

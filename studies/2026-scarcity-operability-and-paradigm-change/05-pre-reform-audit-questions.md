# Pre-Reform Audit Questions

## 1. Purpose

The next Ordivon discussion should not begin with a new repository diagram. It should begin by testing whether current structures encode enduring constraints or historical scarcity.

The audit unit is one existing structure:

- principle;
- primitive;
- repository;
- boundary;
- workflow;
- document class;
- portfolio rule;
- Tool contract;
- governance mechanism.

## 2. Constraint-origin test

For each structure, ask:

1. What failure, scarcity, or coordination cost originally produced it?
2. Is that cause physical, logical, external, technical, or institutional?
3. Has Agent capability, recovery, observability, or reconstruction materially changed the cost?
4. Which real trajectory still fails if the structure is removed?
5. Could a local adapter, evaluator, or recovery mechanism replace a permanent shared abstraction?

## 3. Operability test

Ask which distinctions the current system can now sustain that the old structure collapses:

- multiple branches rather than one next step;
- proposal versus admitted fact;
- implementation versus retained judgment;
- research state versus publication;
- reversible exploration versus committed effect;
- model Session versus durable Task;
- provider implementation versus semantic responsibility;
- participant capability versus consequence exposure.

A new distinction should enter architecture only when it changes decisions, evidence, or recovery in real workloads.

## 4. Bottleneck test

For each project or workflow, identify the present limiting factor:

```text
generation
validation
execution
integration
attention
world access
coordination
stewardship
irreversible consequence
```

Do not optimize the historically expensive stage by default. Measure the current stage that dominates useful progress.

## 5. Coupling test

List functions currently bundled together and test whether they can now vary independently.

Examples:

- Computer as research repository, ontology, experiment owner, and project governor;
- Host as durable work owner and provider-specific Agent loop;
- Harness as cognition loop and long-term state owner;
- Web article as publication and canonical research state;
- repository boundary as both implementation ownership and conceptual boundary;
- Security as protection, control, adversarial research, and authority policy.

For every proposed split, identify the independent failure mode and consumer. For every proposed merge, identify the duplicated responsibility and lost boundary.

## 6. Projection test

Treat documents, dashboards, articles, Issues, and graphs as projections of underlying state.

Ask:

- What is the authoritative state?
- Which views are generated or manually maintained?
- Can two views contradict each other?
- Is the cost of preserving the underlying structure lower than repeatedly reconstructing it?
- Does a richer internal state improve actual continuation, or only make the repository look systematic?

This test protects against both document sprawl and premature knowledge-platform construction.

## 7. Dimensionality test

A representation may be too low-dimensional when it repeatedly loses consequential distinctions. It may be too high-dimensional when its maintenance exceeds the decisions it improves.

For each candidate dimension, require:

```text
repeated lost distinction
+ consequence or duplicated work
+ bounded representation
+ consumer
+ deletion condition
```

Node and relation counts are not evidence of value.

## 8. Reform sequencing

A later reform should proceed in this order:

```text
1. Reconstruct current responsibilities and costs.
2. Identify historical-scarcity assumptions.
3. Locate current bottlenecks and lost distinctions.
4. Compare delete, localize, merge, split, and retain options.
5. Test the smallest high-leverage changes in real work.
6. Update project boundaries only after evidence.
7. Compress stable conclusions into Knowledge or Core.
```

## 9. Required outputs of the later discussion

The reform discussion should produce:

- a current scarcity and bottleneck map;
- a list of obsolete or unproven assumptions;
- a responsibility graph across projects;
- a deletion and localization list;
- candidate boundary changes with counterarguments;
- a small number of experiments or migration slices;
- explicit non-goals;
- a decision about which parts of this study deserve promotion.

## 10. Current stop condition

This study stops before:

- editing `core/`;
- opening new implementation Issues;
- moving code between repositories;
- introducing a universal Research Object schema;
- changing the active Ready Frontier;
- renaming projects;
- merging Computer, Harness, Host, World, Game, Security, or Web.

Those actions require the separate reform discussion requested after this material is reviewed.

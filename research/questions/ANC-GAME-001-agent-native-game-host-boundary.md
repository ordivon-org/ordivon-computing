# ANC-GAME-001 — Agent-Native Game Boundary and Host Convergence

## Question

Which game-system layers are fundamentally changed when runtime policy is generated by uncertain, language-capable, persistent Agents, and how should Ordivon expose those changes through one reusable Host without rebuilding the classical game engine or creating a second Game-private Host?

## Why this belongs in Ordivon Computing

This question crosses repository ownership:

- `ordivon-game` owns deterministic virtual worlds, game observations, action spaces, conflict rules, scenario content, and player-facing Agent interaction;
- `ordivon-host` owns durable Goals, Tasks, Host Events, Contexts, Model Invocations, Decisions, admission, Effects, Dispatches, Observations, Verification, Outcomes, and recovery;
- `ordivon-protocol` should carry only contracts proven reusable across workloads;
- future Game, Finance, Security, Edge, robotics, browser, and software-engineering workloads may share Host mechanics while using different world executors.

The current repositories contain a real architectural divergence. Game decisions D-054 and D-062 state that the Team Coordinator is an Ordivon Host workload rather than a second Kernel, yet `ordivon-game` still contains embedded `AgentHost`, `TeamHost`, `HostStore`, Host Journal, Artifact, Task, Effect, Dispatch, Observation, and recovery implementations. Meanwhile `ordivon-host` v0 deliberately freezes multi-Agent scheduling, provider routing, and game-world execution.

Resolving this by changing only one product repository would either hard-code game semantics into Host or preserve two incompatible Host architectures. Computing must therefore hold the comparative model, hypotheses, conformance questions, and promotion criteria.

## Triggering observations

### 1. Classical games already solve much of the deterministic world

Mature game systems already provide strong solutions for:

- state transition and simulation;
- physics, collision, navigation, animation, rendering, audio, and input;
- entity/component state;
- deterministic or seeded random rules;
- authoritative server state and network replication;
- save/load, rollback, and replay;
- scripted quests, finite-state machines, behavior trees, utility systems, and GOAP;
- bounded action validation, resource accounting, and victory/failure predicates.

Ordivon should consume or emulate these interfaces for research. It should not rebuild a general renderer, physics engine, ECS, networking stack, pathfinder, animation system, or asset pipeline.

### 2. Agent-era change is not merely “deterministic versus probabilistic”

Classical games already use randomness and probabilistic policies. The deeper change is:

```text
classical design
→ designers largely pre-enumerate behavior policy and authored trajectories

Agent-native design
→ designers specify world rules, capabilities, information boundaries,
  goals, incentives, authority, feedback, and evaluation
→ runtime Agents generate plans, language, coordination, and strategy
```

The world transition should remain authoritative:

```text
s(t+1) = T(s(t), admitted_actions(t))
```

The policy becomes an uncertain runtime component:

```text
a(t) ~ π(observation(t), memory(t), goal(t), context(t))
```

Ordivon Game should primarily research and implement the contract between `π` and `T`.

### 3. The current Game Host duplicates the formal Host

`ordivon-game/src/host/AgentHost` and `ordivon-game/src/team/TeamHost` reproduce many mechanisms already owned by `ordivon-host`:

- durable Goal and Task state;
- Host Event Journal and checked projections;
- Artifact storage;
- Context compilation and retention;
- Provider invocation and replacement;
- Decision admission;
- Effect, Dispatch, Observation, and Verification identities;
- lease/revision protection;
- fresh-process continuation and recovery.

The Game implementations also contain legitimate domain logic:

- actor-visible observations;
- game Objective predicates;
- game Action candidates;
- room, inventory, capability, and resource semantics;
- message reachability inside the world;
- game-specific authority attributes;
- joint-action conflict and compatibility;
- one atomic World TickBatch;
- mission victory, failure, and score.

The research problem is to separate these two sets without a destructive rewrite.

### 4. Ordivon Host v0 is not yet a direct replacement

The formal Host currently proves durable single-Task engineering workloads and explicitly excludes:

- multi-Agent orchestration;
- a general scheduler or DAG engine;
- provider routing;
- a game-world executor;
- multiple Actor-scoped Task streams joined into one atomic domain Effect.

Therefore the correct path is not to import the Python package into Game unchanged. The target is one logical Host contract with workload/domain extensions and multiple deployment forms.

## Current hypothesis

### One logical Host, multiple workload extensions

The long-term architecture should be:

```text
                         Ordivon Host
              ┌──────────────────────────┐
              │ Goal / Task              │
              │ Context / Invocation     │
              │ Decision / Admission     │
              │ Effect / Dispatch        │
              │ Observation / Verify     │
              │ Recovery / Artifact      │
              └─────────────┬────────────┘
                            │ workload ports
          ┌─────────────────┼────────────────────┐
          │                 │                    │
          ▼                 ▼                    ▼
  engineering workload   game workload       finance workload
          │                 │
          ▼                 ▼
  Ordivon Runtime      deterministic game world
```

“One Host” means one semantic ownership and conformance model. It does not require every workload to run in the same language or process. An embedded adapter, sidecar, or remote Host may be valid if it conforms to the same Task, Context, Decision, Effect, Dispatch, Observation, Verification, and recovery contracts.

### Classical engine remains authoritative below the Agent boundary

Game retains ownership of:

- `WorldState` and World revision;
- legal Actions and preconditions;
- state transition and environment advancement;
- physical/resource conflicts;
- deterministic or seeded random effects;
- World Events and Facts;
- mission predicates and game score.

Host retains ownership of:

- durable intent and Task continuity;
- Actor/assignee and Provider identity;
- bounded Context and immutable Model Invocation input;
- structured Decision and deterministic admission;
- semantic Effect and stable Dispatch identity;
- uncertainty, waiting, retry/reconcile policy;
- Observation, independent Verification, and Outcome;
- Host Event, CAS object, lease, revision, and recovery semantics.

A Game workload extension supplies:

- `GameObservationCompiler`;
- `GameActionCatalog`;
- `GameDecisionAdmitter`;
- `GameAuthorityPolicy`;
- `GameCoordinationPolicy`;
- `GameWorldExecutor`;
- `GameResultVerifier`.

### Multi-Agent support should be minimal and non-game-specific

Host may need reusable support for:

- Actor or assignee identity on Tasks and Invocations;
- multiple independent Task streams under one Goal;
- causal dependency and explicit waiting;
- one Coordination Activity that joins admitted Decisions;
- one semantic batch Effect with per-participant receipts;
- Provider selection as durable configuration rather than session state.

Host should not know about Engineer, Medic, rooms, oxygen, spare parts, same-room communication, or Station Zero conflict rules. It should not become a universal organization simulator, game scheduler, or maximal-independent-set solver.

## What Agent-native games require that classical games often simplify

These are candidate reusable problem areas, not an authorization to implement every subsystem now.

### 1. World–Agent contract

```text
World → bounded Observation → Agent
Agent → structured Proposal → admission
admitted Action → World transition → Result/Feedback
```

The contract must define observation scope, action identity, stale-state handling, duration, cancellation, concurrent actions, rejection, verification, and replan feedback.

### 2. Perception, knowledge, and belief

Classical NPCs are often omniscient or limited through hand-written flags. Agent-native games need explicit separation among:

- authoritative World truth;
- observations available to one Actor;
- delivered Messages;
- retained memory;
- Agent claims, hypotheses, and uncertainty.

The first contract need not implement a complete belief-revision system. It must at least prevent unrestricted global-state leakage and distinguish observed fact from model assertion.

### 3. Open strategy over bounded action primitives

Agents should not invent physical authority. The world exposes bounded Actions, while Agents generate open-ended planning, composition, negotiation, explanation, and task decomposition over those primitives.

### 4. Language connected to action

Communication should be able to change information, commitments, Task state, authority requests, and later action. Generated dialogue must not remain a cosmetic subsystem disconnected from memory and behavior.

### 5. Durable memory and learned capability

Potential future games may require episodic memory, semantic memory, relationship state, commitments, reflection, and reusable Skills. The open question is which objects belong to Host, Game, or a separate memory service and which mechanisms are genuinely shared across different game families.

### 6. Multi-Agent coordination

Reusable concepts may include Task ownership, delegation, Message, wait reason, commitment, resource claim, conflict, handoff, and joint Effect. Their semantics must be discovered across multiple games rather than generalized only from Station Zero.

### 7. Player–Agent authority

Agent-native player interaction may use instruction, delegation, approval, denial, pause, takeover, negotiation, and governance rather than only direct avatar control. Host should retain durable authority transitions; Game should define domain consequences and player-facing affordances.

### 8. Distributional evaluation

An uncertain policy cannot be validated by one golden output. Evaluation requires explicit combinations of Scenario Case, Provider, policy, intervention, repetition, cost, invalid-action rate, coordination quality, resource efficiency, recovery, and player experience. Run identity and point-in-time replay are therefore reusable Game evidence, not a separate Host implementation.

## Research program

### Phase A — inventory and conformance map

1. Map every `ordivon-game` Host/Team type to an existing `ordivon-host` or Protocol concept.
2. Classify each type as `reuse`, `game-domain`, `temporary-compatibility`, or `unproven-generalization`.
3. Identify semantic mismatches in Task lifecycle, Context identity, Invocation, Decision, Effect, Dispatch, Observation, Verification, Artifact, lease, revision, and recovery.
4. Freeze a small cross-language conformance vector rather than sharing implementation classes.

### Phase B — minimal Game workload contract

Define the smallest ports required to run one Actor decision and one verified World transition through Host semantics. Do not begin with a general scheduler, workflow DSL, or distributed service.

### Phase C — minimal multi-Actor extension

Prove multiple Actor Tasks and Decisions can join one domain-owned atomic TickBatch without moving game conflict semantics into Host.

### Phase D — dual-run migration evidence

Run one short Station Zero Fixture trajectory through:

```text
current embedded TeamHost
versus
Ordivon Host-conformant Game workload adapter
```

Compare exact Context digests, Decision identities, admitted Proposals, selected joint Effect, World Event, per-Intent Verification, Task outcomes, and terminal World digest.

### Phase E — cross-game falsification

Use at least two substantially different micro-game families before promoting abstractions into the Host or Protocol core:

1. **Station Zero** — resource-constrained teamwork, communication reachability, joint Actions, and player supervision.
2. **Partial-observation social/investigation game** — belief, memory, misinformation, trust, language, and hidden identity.
3. A later exploration/crafting game may test long-horizon planning, Skill reuse, and adaptation.

A mechanism should normally appear in at least two workload families before it becomes a general core abstraction.

## Evidence required for progress

- one ownership matrix that leaves every durable object with exactly one authority;
- no second permanent Host Journal, Artifact Store, Task kernel, Provider lifecycle truth, or recovery framework in Game;
- a conformance vector executable from both Host and Game implementations;
- one-Actor Context → Decision → Effect → World Result → Verification equivalence;
- one multi-Actor joint Effect with independent Actor Tasks and per-Intent receipts;
- replacement of Provider process/session without loss of Task identity;
- fresh Host continuation without Game-private Host state becoming authoritative;
- M1–M5 World replay, deterministic World rules, and player controls remain valid during migration;
- measured evidence that embedded, sidecar, or service deployment is chosen by total complexity rather than architectural preference;
- at least one second game exposes which Station Zero abstractions are actually general.

## Promotion criteria

A Game mechanism may move toward Host or Protocol only when:

1. it is independent of Station Zero nouns and rules;
2. another workload needs the same semantic object or transition;
3. one implementation-independent conformance test can describe it;
4. ownership and failure semantics are explicit;
5. recovery works after process replacement;
6. the abstraction removes more duplicated code and conceptual drift than it introduces.

Until then, it remains a Game-domain adapter or research experiment.

## Non-goals

This question does not authorize:

- rebuilding a general game engine, renderer, physics engine, ECS, networking stack, or asset pipeline;
- inserting language models into every NPC update or animation state;
- replacing deterministic World admission with model judgment;
- moving game-specific Objectives, resources, capabilities, or conflict rules into Host;
- creating a general multi-Agent scheduler, organization model, graph database, or workflow DSL;
- migrating Game to a Python sidecar before a measured adapter experiment;
- preserving `AgentHost` and `TeamHost` as permanent parallel Host architectures;
- deleting the embedded implementation before dual-run equivalence and recovery evidence;
- promoting abstractions based on Station Zero alone;
- treating model rationale, confidence, or dialogue as World fact.

## Repository responsibilities

### Ordivon Computing

- owns this comparative research question;
- maintains the cross-stack ownership model and candidate Protocol contracts;
- defines implementation-independent conformance evidence;
- records negative results and competing deployment hypotheses.

### Ordivon Game

- freezes further general Host expansion inside Game;
- identifies duplicate Host mechanics and game-specific coordination logic;
- supplies the Station Zero workload adapter and dual-run evidence;
- preserves the deterministic World, Scenario Cases, replay, and player-facing semantics.

### Ordivon Host

- evaluates the minimum workload/executor ports and Actor/coordination extensions;
- preserves its thin kernel and avoids game-specific semantics;
- provides durable Task, Context, Invocation, Decision, Effect, Dispatch, Observation, Verification, Artifact, and recovery contracts reusable by Game.

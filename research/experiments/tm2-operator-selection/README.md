# TM2 — Research Taste as Operator Selection

TM2 attacks the next hypothesis after TM1 rejected a static research-taste prompt.

The hypothesis is narrower:

> Research taste may be operationally useful when it changes **which observation operator is applied to the current evidence shape**, rather than when it is presented as additional methodological prose.

Two materially different owner pressures are frozen before live Provider trials:

- Harness `H-NOTOOL`: a concrete no-Tool correction/control failure with an exact error string;
- Security `S-UNKNOWN`: structured Harness uncertainty is collapsed by the CAGE Host-assigned adapter.

For each consumer TM2 compares the same `deepseek-v4-flash` model under two conditions with the same total observation budget:

- **open:** the Agent starts from the owner pressure and exact source path catalog;
- **evidence_first:** before the first Agent turn, the experiment executes exactly two literal Git searches using anchors already explicit in the owner pressure. Those two searches count as two observations and their bytes count toward the same total budget. The Agent receives the results and has only the remaining budget.

No TM0 taste prose is added to either condition.

The deterministic anchors are part of the frozen design, not selected after Provider output. They do not encode the hidden causal oracle. They are literal owner-evidence handles such as an exact failure string, owner class name, or field name.

The experiment asks whether this small operator choice reduces open-ended search cost while preserving or improving causal localization. A positive result would support an operator-selection interpretation of research taste. A null result would show that even apparently sensible evidence-first preprocessing does not improve this model/consumer. A negative result would force another contraction.

TM2 remains research-only. It does not promote a query planner, meta-reasoning engine, or global research scheduler.
